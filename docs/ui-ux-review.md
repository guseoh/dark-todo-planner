# Dark Todo Planner UI·UX 개편 검토

현재 기능을 더 늘리기 전에, 실제 사용 시 불편한 정보 밀도와 작업 동선을 줄이는 것을 우선한다. 이 문서는 `main`의 React 화면 구조와 현재 Production 사용 흐름을 기준으로 한다. 밝은 테마는 범위에서 제외하고 다크 모드만 다룬다.

## 개편 원칙

- **실행 화면은 빠르게:** 오늘, Inbox, 전체 Todo는 입력·검색·선택·상태 변경까지 이동 횟수를 줄인다.
- **관리 화면은 조밀하게:** 카드가 화면을 과도하게 차지하지 않도록 높이, 패딩, 버튼, 배지를 줄인다.
- **파괴 작업은 숨기지 않되 안전하게:** 선택/전체 삭제를 명시적으로 노출하되 실제 동작은 휴지통 이동으로 유지한다.
- **모달은 편집에만:** 목록을 고르고 반복 작업하는 흐름은 큰 Modal에 넣지 않는다.
- **색은 역할만 구분:** 기본 화면은 거의 검은 남색 계열, 인디고/보라는 선택·주요 액션, 에메랄드는 완료, 앰버는 경고, 빨강은 파괴 작업에만 쓴다.
- **기능 계약은 유지:** 이번 개편은 Todo/Project/Planning/Memo/Backup 데이터 모델과 API를 새로 확장하지 않는다.

## 화면별 검토와 반영 방향

### 공통 프레임

기존 화면은 강한 남색 그라데이션, 큰 radius와 shadow, 높은 입력창·버튼이 겹치면서 실제 데이터보다 UI 컨테이너가 먼저 보였다.

이번 개편에서는 배경을 더 어두운 단색에 가깝게 낮추고, 카드와 입력창의 radius·높이·shadow를 줄인다. Header 높이와 앱 최대 폭도 줄여 콘텐츠 밀도를 올린다. 공통 Modal은 viewport 안에서만 커지고 본문 내부만 스크롤하도록 변경한다.

### 내비게이션

기존 Sidebar는 10개 메뉴가 같은 중요도로 이어져 화면 목적이 한눈에 구분되지 않았다.

데스크톱에서는 다음 세 그룹으로 나눈다.

- 실행: 오늘, Inbox, 계획
- 보기: 주간, 월간, 프로젝트, 전체 Todo
- 기록·관리: 메모, 휴지통, 설정

`앱 정보`는 실제로 자동화·리마인더·데이터 관리 기능까지 포함하므로 `설정`으로 이름을 바꾼다. 모바일에서는 기존 가로 스크롤 구조를 유지해 기능 접근성을 잃지 않는다.

### 오늘

오늘 화면의 현재 정보 구조는 이미 카테고리 필터와 한 목록 중심으로 정리되어 있다. 이번에는 전면 재설계보다 공통 카드·버튼·Header 밀도 개선을 적용한다. 이후 실제 사용에서 요약 카드가 여전히 크다고 느껴지면 완료율을 한 줄 요약으로 더 축소할 수 있다.

### Inbox

Inbox의 핵심은 빠르게 저장한 뒤 오늘/내일/Someday/Waiting으로 보내는 것이다. 기능 흐름은 유지하고 공통 버튼·카드 밀도를 낮춘다. 추가 분류 기능은 이번 개편에서 넣지 않는다.

### 계획 · 시간 계획

Daily Planning, Weekly Review, Smart View, Template과 Focus/Time Blocking은 이미 역할이 분리되어 있다. 기능을 다시 섞지 않고 상위 탭 구조를 유지한다. 공통 다크 팔레트와 컨트롤 밀도만 우선 개선한다.

`PlanningPage`와 `TimePlanningPanel`은 파일 크기가 커졌으므로 향후 코드 정리 시 섹션 컴포넌트로 분리할 후보지만, 이번 UI 작업과 동시에 대규모 구조 변경은 하지 않는다.

### 주간 · 월간

주간 7일 보드와 월간 Calendar + Side Panel은 시간축 탐색이라는 목적이 명확하다. 현재 기능 동선을 유지하면서 공통 카드/버튼 스타일을 더 조밀하게 만든다. 달력 자체를 새 UI로 갈아엎는 작업은 사용법을 익힌 뒤 실제 불편이 확인될 때 진행한다.

### 프로젝트

프로젝트 화면은 프로젝트 선택 → Overview → Milestone/Memo/Decision → Kanban의 정보량이 많다. 지금 단계에서 기능을 제거하지 않고 공통 밀도 개선만 적용한다. 추후 실제 사용 후에는 Overview와 기록 영역을 탭 또는 접기 영역으로 나눌 수 있다.

### 전체 Todo

이번 개편의 가장 큰 변경점이다.

기존 `선택 작업`은 큰 Modal 안에 전체 Todo 목록과 네 개의 대형 일괄 변경 카드가 들어가 삭제 버튼이 아래쪽에 묻혔다. 기능은 있었지만 사용자가 선택/전체 삭제를 발견하기 어려웠다.

이를 다음 구조로 바꾼다.

- `선택 작업`을 누르면 **현재 화면 자체가 선택 모드**로 바뀐다.
- 실제 Todo 행 앞에 체크박스가 나타난다.
- 선택 모드에서는 카테고리를 강제로 펼쳐 선택 대상을 바로 볼 수 있다.
- 상단 작업 바에서 `현재 결과 선택`, `전체 선택`, `선택 해제`를 제공한다.
- 파괴 작업을 별도 행에 직접 노출한다.
  - 선택 N개 삭제
  - 현재 결과 전체 삭제
  - 전체 Todo 삭제
- 삭제는 영구 삭제가 아니라 기존 Todo Trash로 이동한다.
- 프로젝트/실행일/상태/우선순위 변경은 `선택 항목 일괄 변경` 안으로 접어 기본 화면을 작게 유지한다.
- 전체 Todo는 카드 보드보다 관리에 적합한 **세로 리스트 레이아웃**을 기본으로 사용한다.
- 빈 카테고리를 굳이 모두 표시하거나 이 화면에서 새 카테고리를 만드는 동선은 제거한다.

### 메모

새 메모 작성 폼이 목록 위를 밀어내지 않도록 `새 메모` Modal로 옮긴다. 메모 카드는 한 화면에 더 많이 보이도록 패딩·미리보기·아이콘을 줄이고 최대 3열을 사용한다. 제목/본문 클릭 수정, 고정, Todo 변환, 체크리스트 변환, Todo/Project 연결 기능은 그대로 유지한다.

### 휴지통

복원 Preview는 중요한 안전 기능이라 유지한다. 공통 Modal 크기가 줄어 복원 검토 화면도 viewport를 과도하게 덮지 않게 된다. 영구 삭제와 비우기는 계속 명시적 확인을 거친다.

### 설정

자동화, Discord 리마인더, 데이터 현황, Export는 기능을 유지한다. Sidebar 이름만 `설정`으로 맞춘다. 이후 사용법 검토 후 운영 정보와 데이터 관리 영역을 별도 탭으로 나눌지는 실제 사용 빈도를 보고 결정한다.

## 코드 구조 검토

전체적인 도메인 분리는 유지할 가치가 있다.

- `useTodos`, `useProjects`, `usePlanning`, `useTimePlanning`, `useMemos`, `usePlannerSettings`처럼 데이터 책임이 훅으로 분리되어 있다.
- Page와 공통 Component, Worker route도 기본적인 경계가 존재한다.

다만 기능이 늘며 다음 파일은 계속 커지고 있다.

- `usePlannerData.ts`: 앱 전체 훅을 조합하는 허브가 커져 God Hook 위험이 있다.
- `AllTodosPage.tsx`: 필터, 선택, bulk action이 집중되어 있어 이번 UI 개편 후 별도 Bulk Toolbar 추출 후보이다.
- `PlanningPage.tsx`: Daily/Weekly/View/Template 섹션 분리 후보이다.
- `TimePlanningPanel.tsx`: Timer와 Time Block 영역 분리 후보이다.
- `MemoPage.tsx`: Memo Form/Card/List를 별도 파일로 추출할 수 있다.
- `ProjectPage.tsx`: Overview/Milestone/Decision/Kanban을 섹션 컴포넌트로 나눌 수 있다.

이번에는 UI 변경과 코드 대수술을 동시에 하지 않는다. 먼저 실제 화면의 사용성을 안정화하고, 사용법을 익힌 뒤 자주 수정되는 화면부터 컴포넌트를 분리한다.

## 검증 기준

- 전체 Todo 선택 작업이 Modal 없이 현재 목록에서 끝나야 한다.
- 선택 삭제·현재 결과 전체 삭제·전체 삭제가 스크롤 없이 바로 발견되어야 한다.
- 삭제된 Todo는 기존 휴지통/Restore Preview 경로를 사용해야 한다.
- 선택 모드에서 카테고리가 접혀 있어도 Todo 선택이 막히지 않아야 한다.
- Memo 작성이 목록 높이를 밀어내지 않아야 한다.
- 공통 Modal은 화면 높이를 넘어가지 않고 본문만 스크롤되어야 한다.
- 모바일 390px 수준에서 페이지 자체 가로 overflow가 생기지 않아야 한다.
- Typecheck, Test, Build/Wrangler dry-run, production dependency audit를 모두 통과해야 한다.
- `main` 배포는 Production D1 migration, Worker deploy, `/api/health`가 모두 성공한 뒤 완료로 본다.
